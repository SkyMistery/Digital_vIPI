# Vipi.DbSeed

Copia i dati del DB **SQLite locale** nel **Postgres hostato** (Neon), in modalità **wipe + reseed**.

Serve per far partire il deploy con i dati reali che hai in locale, invece di un DB vuoto.

## Come funziona

- Legge ogni tabella dal file `vipi.db` (solo scalari + FK).
- `TRUNCATE` di tutte le tabelle di destinazione (`RESTART IDENTITY CASCADE`).
- Reinserisce tutto in un solo `SaveChanges`, **preservando gli ID** (le PK sono forzate a
  `ValueGenerated.Never`, le colonne Postgres sono `GENERATED BY DEFAULT` → insert esplicito ammesso).
  EF ordina gli INSERT rispettando le FK e gestisce il ciclo `Document↔DocumentVersion`.
- Risincronizza le sequence identità (`setval`) così i prossimi insert dell'app non collidono.
- I `DateTime` vengono normalizzati a `Kind=Utc` (Npgsql su `timestamptz` lo pretende).

Lo schema di destinazione **deve già esistere** — lo crea `EnsureCreated` all'avvio del deploy.
Questo tool **non** crea schema.

## Uso

Dry-run (nessuna scrittura, stampa solo i conteggi):

```
dotnet run --project tools/Vipi.DbSeed -- "src/Vipi.Host/vipi.db" --dry-run
```

Seed reale:

```
dotnet run --project tools/Vipi.DbSeed -- "src/Vipi.Host/vipi.db" "<connstring-Neon>"
```

La connstring accetta sia il formato keyword Npgsql
(`Host=...;Database=...;Username=...;Password=...`) sia un URL `postgres://user:pass@host/db`
(copincolla da Neon). `SSL Mode=Require` viene aggiunto se assente.

> ⚠️ **Distruttivo**: cancella tutto il contenuto delle tabelle di destinazione prima di ricaricare.
> La connstring è la stessa impostata su Render come `ConnectionStrings__Vipi` (dashboard Neon).

## Note

- Fai girare il deploy almeno una volta prima del seed, così lo schema esiste.
- Se l'app sta scrivendo mentre giri il seed, fermala (il free tier Render dorme dopo 15 min).
- Il file `vipi.db` viene letto: chiudi l'app locale per evitare lock SQLite.
